# RedTeam 控制台页面信息架构评审

> 评审日期：2026-10-18
> 评审对象：控制台 9 个页签（资产测绘 / 智能体 / 会话隧道 / 漏洞战果 / 攻击链 / 得分目标 / 报告 / 知识库 / 技能库）及其全局框架。
> 视角：**正在做演练的红队操作员**，不是审计员、不是开发者。
> 说明：下文只引用聚合数字和页面结构，不复述具体凭据、口令与内网地址。

## 0. 结论

**数据本身不臃肿，臃肿的是“同一层级把所有数据都摊开”。**

当前控制台把三类内容混在了同一层：

1. **操作数据**（现在就要看）：靶标、阶段、分数、下一步打谁、可用隧道/WebShell、卡点、正在跑的智能体。
2. **审计数据**（交付/复盘才看）：132 条漏洞、51 条得分复现、原始请求、攻击链步骤、完整报告。
3. **调试/管理数据**（配置时看）：6 份完整提示词、并发上限、18 个技能的文件路径、版本/更新、SQLite 统计。

红队操作员在演练中真正想回答的只有四个问题：

- 现在打到哪了、拿了多少分？
- 下一步最值得打什么？
- 我手上有什么能用的入口？
- 哪里卡住了、需要我提供什么？

现在的 9 个页签里，只有“得分目标”和“会话隧道”部分回答了前三个问题；其余大量内容需要用户自己交叉比对。

**建议：默认给一个“态势”页，9 个页签收敛为 5 个；把审计/调试内容降级到抽屉或设置。**

## 2. 逐页评审

### 2.1 资产测绘

**现在展示**：45 个 C 段侧栏、174 行资产表（默认 limit 400）、6 个统计数字、8 个筛选器、8 列表格、当前测试入口、底部全局统计。

**红队用户想要**：现在最值得打的 10 台资产；它们为什么值得打；哪些还没评估；点开能看详情。

**问题**：

- 左侧 45 个 C 段占了约三分之一面板宽度，但用户真正要的是“下一批目标”，不是完整 C 段目录。
- 表格同时塞了 IP、发现时间、易打性、测试状态、端口、指纹、标题等列；侧栏宽度下多数列被截断（截图里只能看到 5 列左右）。
- 默认“易打性优先”会把 72 台“未评”资产压到后面；用户看到的是已测过的资产，而不是待办。
- “当前测试”与资产列表是两种视图，但入口混在 C 段分组里，状态为 0 时仍然占位。
- 底部“C 段 45 / 资产 174 / 端口 608 / 指纹 229 / 漏洞 132 / 被动主动 660/1811”与顶部统计重复。

**建议**：

- 默认进入“下一步 10 台”：按“未评 + 高价值系统类型 + 暴露面”排序，每行给：IP、标题、关键端口、建议得分点、为什么。
- C 段侧栏改为可折叠的“C 段筛选”下拉；默认不展开 45 项。
- 表格只保留 5 列：资产 / 关键服务 / 状态 / 易打性 / 下一步；其余进详情抽屉。
- 把“未评”做成独立队列（`待评估 72`），不要和“已测/已放弃”混排。
- 当前测试无任务时隐藏，而不是显示空面板。
- 底部统计移到“态势/概览”或 tooltip，不在每个页面重复。

### 2.2 智能体

**现在展示**：并发上限设置、6 个角色说明、完整提示词编辑器（6 份全文，页面可见文本约 10.8K 字符）、恢复默认/保存按钮。

**红队用户想要**：谁在跑、跑到哪、上次拿到了什么、下一个派谁；提示词是配置，不是操作界面。

**问题**：

- 提示词全文占了页面绝大部分；用户要滚很久才能看到状态。
- 角色说明是静态介绍，和“当前在跑什么”没有关联。
- 并发配置是低频设置，放在操作页顶部。
- 6 个角色写“六个角色”，但实际是 1 个主会话 + 5 个执行角色；语义可以更清楚。

**建议**：

- 默认显示“智能体编队”：每个角色一张卡，字段：状态（空闲/在跑/失败）、当前任务、上次回报摘要、最后活动时间、占用名额；底部“派下一个”按钮。
- 并发上限、提示词编辑器、恢复默认移到“设置”抽屉；提示词按角色折叠，默认只看标题与更新时间。
- 把“主会话”和 5 个执行角色分区，不要混在一个“六个角色”列表里。
- 增加“最近 5 次派活”时间线，替代静态角色说明。

### 2.3 会话隧道

**现在展示**：WebShell 1/1、隧道 3/3、凭据 76、访问会话 6；WebShell 卡片含 URL、类型、**明文连接口令**、资产、权限、凭据引用、最后检测、整段检测说明；3 条隧道卡片含监听地址、类型、可达网段、入口、备注（每段数百字）；凭据/访问会话子页。

**红队用户想要**：现在有哪些入口可用、怎么连、能到哪；不能用的标出来；不要把口令和长备注铺在首屏。

**问题**：

- WebShell 口令、凭据明文直接展示；报告默认脱敏，面板不脱敏，口径不一致，也不安全。
- 隧道备注是“取证/复盘”文本，包含大量内部 IP、PID、哈希、绕 IPS 细节；操作时只需要“监听地址 + 可达网段 + 状态 + 最后检测”。
- 顶部写“还没有可用的 suo5 隧道”，但下面明明有 3 条 active 的 chisel 隧道；用户会误以为没有隧道。这句应改为“没有 suo5 通道；现有 3 条 chisel 可用”或只在完全无可用隧道时出现。
- 凭据 76 条、访问会话 6 条放在同一页，信息量过大；多数凭据是复用素材，不是“当前入口”。
- “复制 URL / 标记失效 / 建立命令 / 走这条隧道扫描”按钮很多，首屏动作不聚焦。

**建议**：

- 首屏只放“入口摘要”：WebShell 数量/在线、隧道数量/可用、凭据数量/最近使用、访问会话数量；每条入口一行：类型 + 地址 + 可达 + 状态 + 最后检测 + 复制。
- 口令默认 `••••`，点“显示”才展示；增加“复制凭据”但不默认渲染。
- 备注折叠，详情抽屉里展示；首屏隐藏内部 IP/哈希/PID 等取证细节。
- 修正 suo5 提示：区分“无任何可用隧道”和“有隧道但不是 suo5”。
- 凭据/访问会话移到“资源/入口”子页，不与隧道混排；默认只显示最近 10 条。

### 2.4 漏洞战果

**现在展示**：6 个统计数字、4 个子页（漏洞 132 / 攻击文件 68 / 凭据 76 / 访问会话 6）、70 个目标分组、每条目标显示前两条漏洞标题 + “+N”、状态/等级/资产标签。

**红队用户想要**：哪些漏洞真正能得分/已利用；哪些只是候选；哪些需要补证据；不要按“漏洞库”方式展示全部 132 条。

**问题**：

- 页面叫“漏洞战果”，但“攻击文件/凭据/访问会话”不是漏洞，信息架构混在一起。
- 默认按目标聚合是对的，但每个目标仍展示漏洞标题 + 数量；70 组全展开会非常长。
- 85 已确认 / 42 已利用 / 38 严重 / 28 高危 / 31 中危 / 103 拿到权限：这些数字是不同维度（状态/等级/成果），并排展示容易被当成同一层。
- 大量 candidate/false-positive 与已利用混在一起；用户要的是“能得分的”，不是“发现过的”。
- 与“攻击链/得分目标/报告”重复：同一个成果在四个页面各出现一次。

**建议**：

- 默认只显示“已利用/可计分”的成果；候选与误报放筛选器。
- 目标分组默认折叠，只显示：目标、最高等级、已利用数、得分点、证据缺口；点开再看漏洞列表。
- 把“攻击文件/凭据/访问会话”移到“入口/资源”，不要放在“漏洞战果”。
- 统计改为两组：**成果**（已利用、可计分、缺证据）与**覆盖**（严重/高危/中危），不要并排混。
- 每条漏洞只保留：标题、目标、状态、得分点、证据状态；原始请求/复现放详情抽屉。
- 与报告/得分目标做“同一数据源、不同视图”，不要在三个页面重复完整列表。

### 2.5 攻击链

**现在展示**：5 个阶段、阶段目标、累计分、本阶段命中、每条命中（分值、得分点、目标、动作、推断/不计分标签）、阶段资产列表、隧道列表。

**红队用户想要**：一条时间线：先做了什么、拿到什么、下一步是什么；不是把所有资产和命中再列一遍。

**问题**：

- **信息收集阶段下面列出 15 台“拿到分数的资产”并显示 +分数，但阶段累计是 0**；语义错误——这是全靶标资产，不是信息收集阶段的成果。
- 阶段内出现 `+0`、`服务已拿满 · 不计分` 的条目，稀释了“真正拿到分”的信息。
- 每条命中带“动作：…（推断）”，长文本多；用户需要的是“哪台、什么成果、多少分、是否可复现”。
- 阶段资产列表与得分目标/资产测绘重复。
- 5 个阶段 + 两套链路 A/B 切换，信息密度高；用户可能只需要当前链路。

**建议**：

- 信息收集阶段只显示“收集了多少资产/域名/网段、关键发现”，**不显示得分资产和分数**；把“拿到分数的资产”移到“得分目标/报告”。
- 只显示计分命中；`+0`/capped 条目折叠到“未计分（N）”。
- 每条命中一行：得分点 + 目标 + 分值 + 证据状态；动作/推断放详情。
- 阶段资产列表去掉，改为“涉及资产 N 台”+ 跳转。
- 默认只保留一条主链路，链路 B 作为“对比/备选”折叠。

### 2.6 得分目标

**现在展示**：总分 10300、25 个得分点、51 次命中、11 条不计分；8 个类别分组；每条得分点显示分值、长名称、命中/上限、已得分；按分值从低到高。

**红队用户想要**：哪些高分点还没拿、离拿满差多少、下一步打哪个；不是按规则文档顺序读 25 条。

**问题**：

- 按分值从低到高排序，和“先打高分”的操作目标相反；用户要先翻过 10/50 分项才看到 1000/5000 分项。
- 长名称（如“邮箱系统 / 办公自动化系统和业务生产系统 / 其他 Web 应用系统权限”）占据大量横向空间。
- “上限 440/600”标签含义不清：440 是已得还是剩余？600 是上限；应写成“已得 440 / 上限 600”+进度条。
- 未命中的类别（工业互联网、物联网、云平台、安全设备等）全部展开，占页面大部分；这些是“覆盖清单”，不是当前待办。
- 与攻击链/报告重复展示阶段和分值。

**建议**：

- 默认“下一步得分”：按“未拿满 + 高分值 + 有可行入口”排序，只显示 Top 5–8；每条给：得分点、当前/上限、差多少、建议资产、为什么现在能打。
- 8 个类别默认折叠，只显示该类别已得/上限；点开再看条目。
- 长名称用短名 + tooltip；表格列改为“得分点 / 已得 / 上限 / 差距 / 下一步”。
- 增加“按阶段”视图（互联网/边界/内网/靶标），与报告四段一致；不要和“按规则类别”混在一起。
- 明确“25 个得分点”与“8 个类别”的关系；不要用“上限合计”暗示可跨项累加（规则明确各项独立）。

### 2.7 报告

**现在展示**：合计 10300、51 项、23 项带原始请求、可复现 21/51、11 条不计分；4 个阶段卡片（8/2/27/14 项，累计分）；四段式全文折叠；复制/下载/重新生成。

**红队用户想要**：一份能直接交的报告；提交前知道哪些条目不可复现、缺什么；不是把报告全文和阶段卡片同时铺开。

**问题**：

- “可复现 21/51”是负面 headline，却没有“另外 30 条缺什么”的清单；用户无法据此补证据。
- 阶段卡片与四段式全文重复；全文很长，侧栏里阅读体验差。
- 报告页与得分目标/攻击链高度重复。
- “23/51 带原始请求”与“可复现 21/51”两个口径并列，用户不清楚差异。
- 报告是交付物，应该以“下载/预览”为主，而不是操作页。

**建议**：

- 首屏只放：总分、四段式目录、可复现率、**缺口清单**（缺原始请求/缺命令/缺截图，按条目列出，可一键跳转补录）、下载按钮。
- 阶段卡片折叠为一行摘要；四段式全文只在“预览/全屏”打开，不在侧栏内联。
- 统一“可复现”口径：一条 = 有目标 + 有结果 + 有命令/报文 + 有证据；把两个数字合并成一个。
- 提供“导出前检查”清单：未复现 N 条、缺证据 N 条、凭据未脱敏 N 条。

### 2.8 知识库

**现在展示**：352 条 POC/EXP、304 已验证、31 次复用、66 条未归类、14,058 个模板；13 个归类卡片；20+ 个来源靶标下拉；类型/验证筛选；长标题卡片。

**红队用户想要**：快速找到“当前目标/组件能用的 POC”；不是浏览全库 352 条。

**问题**：

- 首屏是归类卡片 + 来源靶标列表 + 类型/验证筛选，搜索框不突出；用户要的是“搜组件/CVE”。
- 20+ 个来源靶标（含其它单位）出现在下拉里，既长又涉及跨靶标信息；默认当前靶标是对的，但“全部来源”列表应折叠/搜索。
- 每张卡片标题很长（文件名式），首屏信息密度高。
- “14,058 个模板”“66 条未归类”是库存指标，不是操作信息。

**建议**：

- 搜索框置顶、默认聚焦；支持 CVE / 组件 / 关键字 / 目标。
- 默认筛选“当前靶标 + 已验证”；来源靶标改为可搜索下拉，不展开 20+ 项。
- 归类用 chips，不占首屏大块；列表改为紧凑行：标题（截断）、类型、验证、来源、复用次数；点开抽屉看全文。
- 库存指标收进“统计”小字或 tooltip。
- 增加“最近使用 / 推荐给当前资产”区块。

### 2.9 技能库

**现在展示**：18 个技能、可用 18、2 个目录；每张卡含名称、可用状态、长描述、来源类型、绝对路径；底部“技能目录（DSH 原生）”重复来源与数量。

**红队用户想要**：哪些技能能用、哪些缺依赖、缺什么；不需要每个技能的长描述和本机绝对路径。

**问题**：

- 卡片式长描述 + 绝对路径是开发者/运维信息；红队操作员只需要“可用/缺什么”。
- “只看本插件自带（5 个）”“共 18 个技能 · 来自 2 个目录”“技能目录”三处重复统计。
- 技能可用性检查是低频操作，放在操作页顶部。
- 没有按角色/阶段分组，18 个平铺；用户不知道“现在该用哪个”。

**建议**：

- 默认紧凑表：技能 / 状态 / 缺什么 / 适用阶段 / 一句话；异常项置顶。
- 路径、来源目录、版本放详情抽屉或设置。
- 增加“按角色/阶段”筛选（信息收集/漏洞发现/利用/内网/报告）。
- “重查可用性”放设置或右上角小按钮；不要占首屏。

### 2.10 全局框架

**现在展示**：9 个页签（侧栏宽度下折成两行）、靶标下拉（170px，长名称截断）、版本/检查更新/刷新/全面浏览/收起、页脚全局统计、未读红点。

**问题**：

- 9 个页签在 540px 侧栏里排两行，认知负担高；用户要来回切。
- “全面浏览”是数据密集页的更好形态，但入口在右上角，不显眼；默认仍是窄侧栏。
- 靶标下拉 170px，长单位名截断；45 个靶标没有搜索。
- 版本/更新/刷新/收起与作战无关，占头部。
- 页脚全局统计与页面内统计重复。
- “攻击链/得分目标/报告”三页都在讲阶段与分数；“漏洞战果/会话隧道/知识库”边界不清。

**建议**：

- 页签收敛为 5 个：**态势 / 资产 / 成果 / 报告 / 资源**。

## 14. 深色模式选中按钮对比度修复（2026-10-19）

问题：深色主题的 `--dsw-alias-brand-primary` 是近白色（#f9fafb），旧样式用“品牌色实底 + `color:#fff`”，导致选中的主按钮/一级分区变成纯白底 + 白字。

修复：

- 主按钮、一级分区、`rt-rep-step-no` 的实底文字改为 `color: var(--dsw-alias-bg-base)`（浅色主题是白字，深色主题是深字）；
- 进一步用 `light-dark()` 按 `color-scheme` 分两套：
  - 浅色：品牌深底 + 页面底色白字；
  - 深色：品牌色文字 + 品牌 16% 混入深色层，避免纯白底，也避免白字；
- 覆盖 `.rt-btn-primary`、`.rt-tab-group.on`、`.rt-tabs-groups .rt-tab-group.on` 及其 hover；
- 不支持 `light-dark()` 的浏览器回退到 `background: brand; color: bg-base`，仍然可读。

验证：深色下选中按钮实测 `background ≈ #494a4b`、`color #f9fafb`；UI 117/117、全套 770/770。
