# RedTeam 智能体提示词与红队逻辑审计

> 审计日期：2026-10-18
> 范围：`preset/agent.cordis.yml`、`preset/worker.cordis.yml`、`redteam-store/lib/core.js` 的 `DEFAULT_PROMPTS`、`redteam-tools` 工具契约、`redteam-ui` 提示词页、`score-rules.js` 计分口径。
> 结论只针对“提示词与编排逻辑”，不评价具体靶标的战果。

> 说明：本审计是 2026-10-18 修复前的基线；修复后的状态见文末「7. 修复进展」。修复后六角色提示词总量为 41,950 字（仍在 42K 栅栏内），P0 逻辑修复见该节。


## 0. 结论摘要

1. **不是上下文撑爆，而是低信噪比。** 六个角色提示词合计 40,310 字，其中约 52% 是重复拼接的公共块；主会话/执行角色固定上下文（含 56 个 redteam 工具 schema 34,658 字，不含 DSH 内置 shell/fs/skill 等）按中英混合粗估约 1.9–2.2 万 token。真正的问题是重复、过期代码、互相矛盾的指令，而不是 128K 上下文装不下。
2. **有 8 个 P0 级逻辑/契约问题。** 最严重的是：内网渗透角色被要求“拉起四个子角色”，但执行角色预设没有任何委派工具；隧道可达被当成“边界突破”；资产梳理无法翻页/筛未评估；G5 数据翻倍在工具上不可达；提示词仍在教已废弃的 `core-system`/`boundary`；内网 gogo 命令参数写错；供应链攻击没有授权范围校验；主会话 `plan` 提示词实际未注入。
3. **25 条得分点里，只有 6–8 条有真正的打法。** server-host、web-app、db-credential、central-system、bigdata-system 覆盖较好；domain-control、terminal-access、netdev、cloud-platform、iiot、iot-platform、secdev、file-storage、ai-agent、model-*、computepower-*、boundary-strong/physical/supply 基本只有 code 名，没有工作流。所谓“全面覆盖”目前依赖模型临场发挥。
4. **渗透思路是“瀑布 + 先拿 shell”，不是“得分优先”。** 先收全 → 全量评估 → 漏洞发现 → 利用 → 内网，缺少快速得分轮次和拿点后的再枚举；利用角色把 server-host 排在 web-app/central-system/bigdata 之前，和分值/性价比不一致。
5. **证据链与合规是短板。** G2/G5/G6/G7 没有落到工具字段或检查清单；资产证明靠 `西藏/卫生/医院/gov.cn` 等硬编码关键词判强弱；没有统一的 ROE（禁止破坏、清理、数据最小化）、没有目标内容 prompt injection 防护、没有供应链/第三方授权校验。

### 1.2 臃肿的真正来源

- **公共块按角色各复制一份。** 授权、记分、查库、落库、交付五段在每个执行角色里重复，单角色 2.8K–5.1K 字。代码层只维护一份，但模型层看到的是五份。
- **得分规则在多处重复。** `COMMON_SCORE_RULES`、`redteam_score_hit` 工具描述、`redteam_chain_add` 描述、面板提示词、文档各有一份 code 列表，已经出现漂移（见 2.5）。
- **工具描述与提示词重复。** `redteam_score_hit` 描述 1,124 字，`redteam_tunnel_add` 497 字，`redteam_chain_add` 2038 字 schema；很多内容在提示词里又说一遍。
- **主会话有两份人设。** `agent.cordis.yml` 的 persona 与 `DEFAULT_PROMPTS.plan` 是两套独立维护的文本，已经出现矛盾（见 2.8）。
- **硬编码的“知识”很多。** “13,742 个 nuclei 模板”“61 个 impacket-*”“最多 3 个”“六个角色”等，会随版本/配置腐化。
- **每次新增经验就追加一段。** 42K 栅栏已经接近上限，说明这是“事故驱动 accretion”，不是按角色职责设计的分层。

**判断：** 单角色 2 万 token 固定开销不算致命（128K 上下文约 15–20%），但 56 个 redteam 工具 + 40K 字提示词的组合会显著降低工具选择准确率和指令遵循稳定性。更合理的预算是：主会话 1.5–2K token，执行角色 2–2.5K token，具体战术放技能/工具输出。

## 2. P0/P1 逻辑与契约问题

### 2.1 P0：内网渗透角色被要求派活，但执行预设没有委派工具

- `internal` 提示词：`拉起信息收集智能体…你可以用 subagent 派活；也可以自己按同样方法做，但优先派活`（`core.js:711`），随后又要求“拉起资产梳理/漏洞发现/漏洞利用”（`core.js:715-717`）。
- `redteam-worker` 预设明确不挂任何委派工具（`preset/worker.cordis.yml:8-10`；bundle 测试也断言 `subagent`/`workflow`/`ralph` 都不存在）。
- 结果：内网角色一开局就可能调用不存在的 `subagent`，失败后被迫自己串四个角色；它拿不到“子角色”的独立上下文和工具，内网阶段会退化成一个大杂烩，且与主会话的派活逻辑重复。

**建议：** 二选一，推荐前者：
1. 改写 `internal` 为“自己按四个子阶段执行”，删掉所有“拉起/派活”措辞；主会话只派一个 `internal`，由它顺序完成内网收集→评估→发现→利用。
2. 或者给 `redteam-worker` 加委派工具——但这会破坏“叶子节点”硬约束，并引入并发/递归风险，不建议。

### 2.2 P0：把“隧道可达”当成“边界突破”，1000/10000/30000 分可能被高估

- `exploit`：`拿到 WebShell 后第一件事是建 suo5 隧道…通了才算打进内网`（`core.js:666-667`）。
- `internal`：`boundary（互联网边界突破，隧道可达内网）`（`core.js:727`）。
- 计分规则第 22–24 项要求“进入逻辑隔离/强隔离/物理隔离业务内网”，证明材料是隔离设备控制截图、能访问内网的截图等；**“从互联网 DMZ 主机开一个 socks5 到同段/同区”不是边界突破**。
- 当前实现只看 `entry_kind` 是否 `self-only`（`tunnelIsLegit`），不判断源/目的网络区域，也没有“隔离设备/跨区证据”字段。一个 DMZ WebShell 的隧道就能记 `boundary-logical` 1000 分。

**建议：** 增加“边界判定”硬门槛，至少要求：
- 入口主机所在区域 vs 隧道落点区域（DMZ/办公网/生产网/隔离网）；
- 跨越隔离设备的证据（设备控制截图、路由/策略、网闸/防火墙）；
- 经隧道访问到的**目标内网**资产，而不是入口主机同段。
同区/同段只能记 `internal`，不能记 `boundary-*`。报告阶段也应按同一门槛复核。

### 2.3 P0：资产梳理无法翻页，也无法筛“未评估”，与“3000 条全过”冲突

- `assess` 要求“不允许抽样…有 3000 台就过 3000 台，分批用 `redteam_asset_query` 翻页，按 `sort=todo` 取未评估的”（`core.js:592`）。
- 但 `redteam_asset_query` 的工具参数没有 `offset`（`redteam-tools/lib/index.js:796-820`），`limit` 最大 200；`sort=todo` 是按 `test_status` 排（未测优先），不是按“是否已评估”；`assessAsset` 只写 `priority/assessed_at`，不写 `test_status`（`core.js:2160-2172`）。
- 结果：超过 200 台时模型只能反复看到同一批；已评估的资产仍会出现在 `sort=todo` 前排；它永远无法确认“没有未评估的资产”。

**建议：**
- `redteam_asset_query` 增加 `offset`、`assessed`（yes/no/unassessed）、`sort=unassessed`；
- `assess` 改成“按风险分批”：每轮取 Top N（如 50）高价值/未评估资产，评估完再取下一批，明确“不要求一次过完 3000 台”；
- 评估结果写 `priority/potential/reason` 的同时，写一个可查询的 `assessed_at` 过滤条件。

### 2.4 P0：G5 翻倍在工具上不可达；G6/G7 没有落地；大数据阈值写错

- `score_hit` 的 schema 没有 `data_scale`、`ip_version`（`redteam-tools/lib/index.js:1436-1495`），而 `scoreMultiplierOf` 只在 `hit.data_scale` 为 `large`/`knowledge-base` 时才 ×2（`score-rules.js:407-420`）。schema 未声明、提示词也未提这个字段，正常调用不会传，**G5 翻倍实际上不可达**。
- G6 IPv6 ×3 会按 target 自动生效，但提示词从未提“优先 IPv6 资产”，模型不会主动利用 3 倍规则。
- G7 证明材料（隔离设备截图、路由表、终端归属、托管节点 20%）只在得分点描述里零散出现，没有按得分点列检查清单；`COMMON_SCORE_RULES` 没有 G7 正文。
- `vuln-scan` 写“`bigdata-system` 门槛是 ≥100 万条”（`core.js:636`），规则原文是“有效数据量小于 5 亿条或 1TB 的按普通数据库计算”（`score-rules.js:818-820`）。100 万与 5 亿差 500 倍，会把普通数据库记成 1000 分的大数据系统。

**建议：**
- `score_hit` 增加 `data_scale`（large/knowledge-base）、`ip_version`，并在提示词里写清门槛（翻倍 ≥1 亿条/10TB；大数据系统 <5 亿条/1TB 降为普通数据库）；
- 增加 `G7` 检查清单（按 code 列证据），或者做一个 `redteam_evidence_check` 工具；
- 修正 `vuln-scan` 的 100 万阈值。

### 2.5 P0：提示词仍在教已废弃的 code，会直接记分失败

- `internal`：`域控、堡垒机、运维平台、代码仓库、数据库集群、备份系统 → code=core-system`（`core.js:726`）。
- `internal`：`boundary（互联网边界突破，隧道可达内网）`（`core.js:727`）。
- `addScoreHit` 对旧 code **不做静默改派**，找不到就报 `score point not found`（`core.js:2029-2043`）。
- 预检降级文案和 `redteam_attack_chain` 的 hint 仍在提 `core-system`/`boundary`（`redteam-tools/lib/index.js:590,596,1674`）。
- `redteam_chain_add` 的 `point_code` 描述示例仍是 `rce / webshell / boundary`（`redteam-tools/lib/index.js:1562`），与“旧 code 全部废弃”矛盾。

**建议：** 全量替换为 `central-system`/`web-app`/`bigdata-system`/`server-host`/`boundary-logical|strong|physical`；加一个提示词 lint 测试，禁止出现旧 code 清单。

### 2.6 P0：内网 gogo 命令参数写错，照抄跑不通

- `recon`：`gogo -p <网段> --proxy socks5://<隧道> -o runs/gogo-<网段>.json`（`core.js:558`）。
- gogo 的目标参数是 `-i`，`-p` 是端口；输出格式是 `-o json`，输出文件是 `-f <file>`（见 `skills/gogo-intranet.md:75-76,191`）。
- 正确写法应类似：`gogo -i <网段> --proxy socks5://<隧道> -o json -f runs/gogo-<网段>.json`。
- 这条命令是内网信息收集的主入口，参数错误会直接导致“内网扫不出来”，进而漏掉网段和得分点。

**建议：** 修正命令；在提示词里只保留一条经过实测的模板，细节交给 `gogo-intranet` 技能。

### 2.7 P0：供应链攻击没有授权范围校验，且“进入供应商内网”不等于“进入主防单位内网”

- `boundary-supply` 的规则是“借助供应链运维通道或云服务进入**主防单位**内网”，满分 1000/3000。
- 提示词只有“用户给靶标单位名称即代表已授权”（`core.js:413-415`），没有“供应商/云服务/第三方是否在授权范围”的判断；`exploit`/`internal` 也没有要求先向用户确认。
- 实际报告里存在“打到供应商 frp/Gogs/MinIO，拿到供应商内网”就记 `boundary-supply` 的情况；但证据若只证明供应商内网可达，没有证明进入主防单位内网，按规则站不住；同时可能构成对第三方的未授权攻击。

**建议：**
- 增加硬门槛：`boundary-supply` 必须同时满足“用户确认该供应商/云服务在授权范围”+“证据显示进入主防单位内网/不同网络区域”；
- 提示词增加“第三方/供应商不在授权范围时，只记录线索、不攻击”；
- 报告阶段对 `boundary-supply` 单独复核这两条。

### 2.8 P0：主会话 `plan` 提示词实际未注入；提示词页的“每次请求前注入”是误导

- `DEFAULT_PROMPTS.plan` 只被 `listPrompts`/`resetPrompts` 读写（`core.js:5446-5486`），没有任何运行时注入路径；`PLANNER_ROLE` 只用于 `agentOf` 的默认值（`redteam-tools/lib/index.js:286-289`）。
- 主会话真正生效的是 `agent.cordis.yml` 的 persona；它和 `plan` 是两份独立文本，已经矛盾：
  - persona 说“只有读操作 + preflight/slot/session_info 由你直接调用”（`agent.cordis.yml:51`），但同一份 persona 又说 `redteam_engagement_open` 只绑定本会话（`agent.cordis.yml:82`）；`open`/`bind` 是写操作，按第 51 行被禁止。
  - persona 前半说并发“由用户配置，默认 3”（`agent.cordis.yml:61`），紧接着又写死“总数 ≤ 3”（`agent.cordis.yml:62`）；`plan` 说“硬约束，最多 3 个”（`core.js:499`）；实际上限可配到 10（`settings.js:14`）。
  - persona 写“六个角色”但只列了五个（`agent.cordis.yml:65-72`）。
- UI 提示词页说“保存后…在该角色会话的每次模型请求前注入”（`redteam-ui/lib/client.js:1077-1078`），对 `plan` 不成立；对执行角色也只是主会话手动把 `redteam_role_prompt` 的输出贴进任务描述，不是系统提示注入。
- 老靶标提示词大量残留：本机 45 个靶标中 23 个六角色齐全且为当前版，10 个六角色齐全但至少一个角色仍是旧版，12 个缺文件（10 个缺 `plan`/`assess`，2 个没有 `agents/` 目录）。旧版里甚至有“够用就停”与当前“收集完整”完全相反的口径。

**建议：**
- 二选一：把 persona 作为唯一主提示词，删除/归档 `plan` 默认文本；或者让 persona 动态加载 `plan`（需要运行时注入机制）。不要维持两份。
- UI 文案改成“保存后由主会话在派活时读取并写入任务描述”，不要承诺自动注入。
- 增加提示词版本/新鲜度检查：`redteam_preflight` 返回 `prompts.stale`，面板显示“旧版”徽标；对已知旧默认做自动升级或一键批量刷新。

### 2.9 P1：目标定义缺失，“靶标权限”可能被任意 Web 登录撑大

- `scoreStageOf` 把所有 `web-app`/`central-system` 强制归到 `target`（`core.js:289-297`），不管它是互联网上的普通 OA，还是演练指定的核心靶标。
- 提示词没有“靶标确认”步骤：没有让用户确认/标注哪些系统是本次演练的靶标，也没有区分“子公司门户”和“主防单位核心系统”。
- 结果：互联网侧随便一个 OA 管理员登录（100 分）就会出现在报告“靶标权限”段，而不是“互联网资产权限”；报告的四段式语义被稀释。

**建议：** 在 `plan`/`internal` 增加“靶标确认”：列出候选核心系统（官网/OA/业务生产/集权/大数据），让用户确认或标注“推断”；报告只把确认过的系统放 `target`，其余按资产位置归 `internet`/`internal`。

### 2.10 P1：资产证明靠硬编码关键词，不是采集到的证据

- `rpAssetProof` 用 `西藏|卫生|医院|疾控|血液透析|护士工作站|基层卫生|妇幼|健康|供应链|OA|HRP` 和 `xzwsjsw|gov.cn|医院|卫生|疾控` 判定标题相关性/强度（`core.js:5795,5822-5827`）。
- 这是某个具体靶标的启发式，却被用在所有报告上：非卫生/非政府靶标会被误判为“中/待补”，任意 `.gov.cn` 会被判“强”，供应商识别也依赖 `frpnat|frp.|fatedier|bskeji` 等硬编码。
- 提示词没有要求信息收集角色采集“归属证明”（ICP 备案、证书、WHOIS、首页版权/页脚、单位名称、截图），报告只能靠名称/标题猜。

**建议：**
- 增加 `asset proof` 采集任务：每个得分资产至少记录一种归属证据（备案号/证书 CN/WHOIS/首页页脚/单位落款），并 `redteam_shot_add` 截图；
- 报告改为读证据字段，删除靶标特定关键词；
- 强弱判定用证据类型+数量，不用关键词。

### 2.11 P1：`recon` 一边说“不碰漏洞检测”，一边让 fscan 打点

- `recon` 开头：“只做资产信息收集…不碰漏洞检测”（`core.js:533-535`），收口又说“只收集，不深挖漏洞”（`core.js:570`）。
- 但内网步骤要求 `fscan` 打点，并明确说它的“弱口令、未授权访问与高危漏洞结果是漏洞发现的线索”（`core.js:560-562`）。fscan 默认会做弱口令爆破、未授权利用、MS17-010 等，已经越过了“只收集”的边界，也可能锁账号、触发告警。
- 这会与 `vuln-scan`/`exploit` 重复劳动，且责任不清。

**建议：** 内网收集只用 gogo 铺面 + fscan 的“只扫不爆”模式（`-nobr -nopoc` 或最小化），弱口令/未授权交给 `vuln-scan`/`exploit`；或者在提示词里明确“fscan 只允许发现，不允许利用”，并给出安全参数。

### 2.12 P1：并发/角色数量文案与实现不一致

- persona 说可配置、默认 3（`agent.cordis.yml:61`）；`plan` 说最多 3（`core.js:499`）；`preset.yml` 说“并发最多 3”；实际 `MAX_AGENTS_LIMIT=10`（`settings.js:14`）。
- persona “六个角色”只列五个；工具描述 `redteam_role_prompt`/`redteam_roles` 仍写“四个角色”；UI “全部恢复默认”写“四个角色”。
- 这些不是核心逻辑，但会让模型/用户对系统能力产生错误预期。

## 4. 渗透思路评估

### 4.1 瀑布式，不是迭代式

`recon → assess → vuln-scan → exploit → internal` 严格顺序，主会话“每步结束再派下一步”。真实红队更像“快速得分轮次 → 拿入口 → 再枚举 → 再利用”的循环：拿到一个凭据后应立刻全资产复用，拿到 WebShell 后应立刻回看资产面/登录面，而不是等全部评估完。当前只有 `internal` 内部有“新网段再跑一轮”的循环，外网没有。

**建议：** 增加“Wave 0 快速得分”（默认口令/暴露数据库/未授权/VPN/供应商/域名）+“每次拿点后触发再枚举”的循环；全量评估改为风险分批。

### 4.2 先拿 shell，不是先拿分

`exploit` 的顺序是“优先服务器权限 → 弱口令 → 会话 → 隧道 → 其它得分”。但分值是：server-host 50、web-app 100、netdev 200、central-system 500、bigdata 1000。一个可登录的集权系统/大数据平台，性价比可能远高于一台普通服务器。服务器权限的价值主要是“进内网的跳板”，不是终点。

**建议：** 在 `exploit` 开头加“得分路径选择”：先按资产类型列候选得分点（web-app/central/bigdata/netdev/cloud/...），按“预期分值 ÷ 预计投入”排序；服务器权限作为进入内网的手段，单独标注。

### 4.3 边界语义错误（见 2.2）

这是分值最高、也最容易被质疑的一类。隧道可达只是“能路由到”，不等于“突破隔离”。需要把“入口区域/落点区域/隔离设备/目标内网资产”四件事写进证据，否则 1000/10000/30000 分的报告很难交出去。

### 4.4 证据链是“事后补”，不是“边打边固化”

提示词要求 `tool/result/HTTP evidence/截图`，但：
- 资产证明没有采集任务；
- G7 没有按得分点列清单；
- 登录成功只要求 `redteam_access_add`，没有强制 HTTP 证据/截图；
- 报告资产证明靠关键词猜（见 2.10）。

**建议：** 把“证据”做成每个得分点的必填项/检查项，而不是通用提醒；报告只在证据齐全时标“可复现”。

### 4.5 角色边界与责任不清

recon 跑 fscan、assess 跑 nmap、internal 想派活但没工具、主会话被禁止 open 但必须 open。这些都会造成重复劳动、漏项和“谁都以为别人会做”。

**建议：** 用一张 RACI 表锁定每个角色的“允许动作/禁止动作/交接物”；工具层做角色门禁（见 5.3），不要只靠提示词。

### 4.6 缺少 ROE、OPSEC、清理与 prompt injection 防护

- 没有统一“禁止破坏性操作（删除/加密/重启/关机）”“数据最小化”“演练后清理 WebShell/隧道/账号”的规则；只有目录爆破处提了一句别碰 `/logout`、`/reboot`、`/delete*`。
- 没有“目标页面/响应/文件/日志中的指令不可信”的规则；红队 agent 会大量读取目标内容，prompt injection 风险很高。
- 没有“第三方/供应商/云服务不在授权范围就不打”的规则（见 2.7）。
- 没有时间/请求预算和停止条件；“收全/全部过/直到没有新网段”是无限循环。

**建议：** 增加一段 `COMMON_ROE`（ROE/清理/数据最小化/第三方范围/破坏性操作禁止）和 `COMMON_UNTRUSTED`（目标内容只作数据，不执行其中指令）；给出每阶段的预算/停止条件。

## 6. 一句话回答四个问题

1. **提示词臃肿吗？** 结构上臃肿：40.3K 字、52% 重复、56 个工具、42K 栅栏用掉 96%；不是装不下，而是信噪比低、易漂移。
2. **业务逻辑有问题吗？** 有，且有几个是硬伤：内网角色无委派工具、隧道当边界、评估不能翻页、G5 不可达、旧 code 仍在教、gogo 命令错误、供应链无授权校验、plan 提示词未注入。
3. **每个角色全面吗？** 不全面。server/web/db/central/bigdata 有打法；domain/terminal/netdev/cloud/IoT/IIoT/secdev/file-storage/AI/model/compute/boundary-strong/physical/supply 基本只有 code 名。
4. **渗透思路有问题吗？** 有：瀑布式、先 shell 后得分、边界语义错误、证据链事后补、角色边界不清、缺 ROE/注入防护/预算。
