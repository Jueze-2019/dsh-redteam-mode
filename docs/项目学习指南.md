## 1. 它是什么：一个"指挥台"，不是一堆脚本

传统红队工具链的问题是**数据散**：扫描器输出在 A 目录、笔记在 B、WebShell 地址记在聊天里、报告最后靠回忆拼。本项目的核心主张只有一句话：

> 把**所有发现**强制落进一个本地 SQLite 事实库，让**智能体、界面、命令行**读同一份数据；一切围绕"得分点"推进，没落库的发现视为无效工作。

于是它做成了三件事：

1. **编排**：DSH 预设 `redteam` 把主会话变成"指挥者"，它不自己动手，而是把扫描/爆破/利用/内网探测委派给四个角色子智能体；
2. **事实库**：`dsh-redteam-store` 发布进程级服务 `ctx.redteam`，承载 22 张表，是唯一的真相来源；
3. **可视化**：`dsh-redteam-ui` 提供常驻右侧栏控制台（11 个页签）+ 一条 host 侧 HTTP 桥接 `POST /redteam/api`。

一次演练的完整形态：

```
用户：<靶标单位名称>
   │
   ├─ 主会话（指挥）：拆解 / 派任务 / 盯进度 / 分析回报 / 决定下一个任务
   │     ├─ 信息收集  recon      域名·子域·C 段·端口·指纹·Web 标题·边界与隐藏资产
   │     ├─ 漏洞检测  vuln-scan  Nday/1day 优先，逐条确认并落原始 HTTP 证据
   │     ├─ 漏洞利用  exploit    拿账号 → 浏览器实测登录 → 遍历功能点 → WebShell / RCE / 数据库
   │     └─ 内网渗透  internal   suo5 隧道 → gogo/fscan 测绘 → 凭据复用 → 横向 → 核心系统
   │
   └─ 全部发现落进 SQLite 事实库（22 张表 + FTS5）
            ↓
      右侧栏控制台 11 个页签（资产测绘 / 攻击链 / 得分目标 / 报告 / 知识库 …）
```

### 1.1 五条贯穿全项目的设计原则

| 原则 | 含义 | 代码里的体现 |
| --- | --- | --- |
| **得分目标驱动** | 动手前先问"这条线能落到哪个得分点"，答不出就不做；明确禁止测与得分无关的 CORS/目录列举/版本泄露类问题 | 预设人设 + `DEFAULT_SCORE_POINTS` + 四个角色提示词 |
| **落库才算数** | 资产/漏洞/凭据/证据/步骤/得分都必须进库，未落库的发现视为无效 | 48 个工具的强制参数（如 `redteam_attack_file_add` 的 `evidence` 必填） |
| **反重复劳动** | 打任何目标前先查 `test_status` / 已有漏洞 / 现成 WebShell·隧道·凭据；测完立刻回写状态 | `COMMON_DB_LOOKUP` 提示词段 + `asset.test_status` + `blocked_count` |
| **入口必须可交付** | WebShell 只要冰蝎马/哥斯拉马（一句话马用户连不上）；打进内网必须建 suo5 隧道并登记 | `webshell.shell_type` 白名单 + `tunnel.entry_kind` + 面板红字提示 |
| **不虚报战果** | 自建账号不计分、自己 VPS 上的代理不算边界突破；所有判定由服务端硬规则兜底，不靠模型自觉 | `self_created` / `tunnelIsLegit()` / `ACCOUNT_POINT_CODES` |

## 2. 功能框架（一）：作战模型

### 2.1 攻击链五阶段（作战地图）

这是全项目的骨架。所有得分和步骤都按**攻击面的位置**归入五个阶段（`DEFAULT_STAGES`，存 `stage` 表）：

| # | code | 名称 | 副标题 | 阶段目标 | 是否计分阶段 |
| --- | --- | --- | --- | --- | --- |
| ① | `recon` | 信息收集 | RECON · 互联网侧 | 在互联网侧展开收集，确定值得打的资产面 | 否 |
| ② | `internet` | 互联网资产权限 | INTERNET-SIDE PRIVILEGE | 在互联网侧资产上拿账号/权限/数据 | 是 |
| ③ | `boundary` | 边界突破 | BOUNDARY BREACH · TUNNEL | 搭隧道，把控制能力延伸进内网 | 是 |
| ④ | `internal` | 内网资产权限 | INTERNAL-SIDE PRIVILEGE | 走隧道在内网资产上拿分 | 是 |
| ⑤ | `target` | 靶标权限 | TARGET SYSTEM | 拿内网核心靶标（域控/堡垒机/核心业务） | 是 |

**得分归属是自动推导的**（`scoreStageOf()`），优先级从高到低：

1. 显式 `stage_code`（`score_hit.stage_code`）；
2. 类型特判 `POINT_STAGE_OVERRIDE`：`core-system → target`、`boundary → boundary`；
3. 按命中资产的内外网归属 `asset.scope`（`internal → ④`、`external → ②`）；
4. 没有 `asset_id` 时按 `target` 里的 IP 判断（私网 → ④，公网/域名 → ②，兜底 ②）。

`asset.scope` 的判定在 SQL 与 JS 两处保持一致（`SCOPE_SQL` / `scopeOfIp()`）：`10.*`、`192.168.*`、`127.*`、`169.254.*`、`172.16–31.*`、`100.64–127.*` 为内网，其余为外网；手工指定优先于自动推导。

> **踩坑史（务必知道）**：v0.4.0 之前的阶段 code 是 `external/foothold/tunnel/privilege`，全部作废。写过废弃值的步骤**不落在任何阶段**（页面计数为 0）。现在服务端用 `VALID_STAGE_CODES = ['recon','internet','boundary','internal','target']` 做白名单校验，非法值退回按 `stage` 兜底映射并回告警（`stage_hint`）。老库在 `migrate()` 里自动清掉废弃值并重建。

### 2.2 得分点模型

`score_point` 表（默认 10 项，合计 **255** 分，界面可增删改）：

| code | 名称 | 分类 | 分值 |
| --- | --- | --- | --- |
| `web-account-user` | 获取 Web 普通账号权限 | 账号权限 | 10 |
| `web-account-admin` | 获取 Web 管理员账号权限 | 账号权限 | 20 |
| `webshell` | 上传 WebShell 并维持访问 | 服务器权限 | 20 |
| `rce` | RCE / 命令执行 | 服务器权限 | 30 |
| `server-shell` | 获取服务器权限 | 服务器权限 | 25 |
| `db-access` | 获取数据库权限 | 数据库 | 25 |
| `sensitive-data` | 获取大量敏感信息 | 数据 | 20 |
| `boundary` | 互联网边界突破 | 网络突破 | 30 |
| `internal-pivot` | 突破逻辑内网（横向移动） | 网络突破 | 35 |
| `core-system` | 拿下核心系统 | 核心目标 | 40 |

**记分规则（服务端强制，不是提示词劝告）：**

- `redteam_score_hit` **必填两样**：`code` + `evidence`（只写结果：目标资产 + 拿到什么，例如 `10.1.2.3｜后台管理员 tomcat/Tomcat@2024`）。缺任一项直接报错。
- **同类不设数量上限**：每次真实命中按分值累加（`命中次数 × 分值`）。
- `score_hit` 可挂 `vuln_id`（报告据此自动附原始请求）与 `step_id`（攻击链连线）。
- **红线一：自己注册的账号不算分**。`self_created=true` 只留痕：`counted=false`、不计数、不进报告。判定集合 `ACCOUNT_POINT_CODES = ['web-account-user','web-account-admin','server-shell','db-access','internal-pivot','core-system']`。
- **红线二：自己的 VPS 不算隧道**。见 2.3。
- 写 `redteam_chain_add` 时带 `point_code` + `evidence` 可**一次调用同时完成"动作入库 + 记分 + 双向关联"**；只给 `point_code` 不给 `evidence`，服务端跳过记分并回 `score_hint` 提示"本次没有记分"。

### 2.3 隧道合法性判定（边界突破的凭证）

`tunnel.entry_kind` 必须说清**目标侧的那一端是什么**，否则 `legit=null`、界面显示"待确认"，**不计入边界突破**：

| entry_kind | 含义 | 算突破？ |
| --- | --- | --- |
| `target-outbound` | 目标主动连出（反弹 shell 落地到我方 VPS、目标上跑 frp/Stowaway 客户端） | ✅ |
| `target-http` | 经目标 WebShell/HTTP 通道（suo5 / Neo-ReGeorg / reGeorg） | ✅ |
| `target-agent` | 经目标已控进程/会话转发（SSH `-R` 由目标发起等） | ✅ |
| `self-only` | 只在自己 VPS / 自建服务器上开的 socks5、frp 服务端、代理 | ❌ 页面标红"不算突破" |
| 留空 | 未声明 | ⚠️ `legit=null`，按待确认处理（不计分） |

判定函数：`tunnelIsLegit(entryKind)`（空 → `null`；`self-only` → `false`；其余 → `true`）。

### 2.4 四个角色智能体

角色提示词按**靶标**存储在 `engagements/<靶标>/agents/*.md`，可由界面编辑、可一键恢复默认（`redteam_role_prompt_reset`）。

| 角色 | code | 职责要点（提示词核心） |
| --- | --- | --- |
| 信息收集 | `recon` | 域名/子域/C 段/端口/指纹/Web 标题；被动优先，够判断得分面就停；收口时对每个资产做**易打性评估**（`priority` + `potential` + `reason`） |
| 漏洞检测 | `vuln-scan` | **Nday/1day 优先**；先查 POC 知识库两层，命中即用；逐条确认并落原始 HTTP 证据；无关水洞不报 |
| 漏洞利用 | `exploit` | 拿账号 → **浏览器实测登录（只有凭据不算拿到账号）** → 逐个功能点找 getshell → 冰蝎/哥斯拉马落库 → 立刻建 suo5 隧道 |
| 内网渗透 | `internal` | 先登记入口再动；gogo 铺面、fscan 打点；凭据复用与横向；冲击核心系统 |

**公共段落由代码注入，不重复写**：`COMMON_SCORE_RULES`（记分纪律）与 `COMMON_DB_LOOKUP`（查库流程）各写一份，`DEFAULT_PROMPTS` 在模块加载时拼到四个角色正文末尾 — 面板/工具/测试拿到的是完整正文，改一处即全生效。

**子智能体是叶子节点（硬约束）**：预设的 `tool-subagent` 行用 `toolFilter.deny` 把 `subagent_fork` / `workflow` / `ralph` 从子会话的工具目录里直接摘掉，再用 `maxDepth: 1` 作二道保险。注意坑：**不能把 `subagent` 本身写进 deny**——它是该行自己注册的 scoped 工具，不在全局工具库，写进 deny 会让 `tools.restrict()` 校验失败、整个委派路径报 "unknown global tool"（v0.8.0 踩过，v0.8.1 修）。

### 2.5 指挥者的行为纪律（写进预设人设）

- **只做四件事**：拆任务、派子智能体、分析回报、决定下一个任务。扫描/爆破/利用/上传/登录遍历/内网探测**一律委派**。例外：若收到的任务描述里带角色提示词，说明自己就是被委派的执行者，此时全力执行、不再下派。
- **优先边缘资产**：官方门户/邮箱/官网通常有 WAF，投入产出比低；优先旁站、兄弟资产、测试/预发环境、老旧系统、非标准端口、VPN/堡垒机/运维平台/暴露数据库、小程序与 APP 后端。
- **被封 >3 次即放弃**：用 `redteam_asset_test`（`status=abandoned` + `blocked=true`）在**同一次调用**里写清原因与剩余面；`blocked=true` 按调用次数累计，**每次被封都要单独记一次**，否则计数永远到不了 3。
- **工具与技能优先，禁止手搓**：扫描用 nmap/masscan/fscan/gogo，指纹用 httpx/gogo，POC 用 nuclei，目录用 ffuf/dirsearch，爆破用 hydra/fscan，隧道用 suo5/chisel，WebShell 用冰蝎/哥斯拉/蚁剑。手搓脚本必须说明为什么现成工具不适用。
- **代理只做命令级临时指定**（`curl --proxy`、`nuclei -proxy`、`ffuf -x`），**绝不改本机网络/代理配置**。

## 3. 功能框架（二）：48 个模型工具

工具在 `packages/redteam-tools/lib/index.js` 注册（`ctx.tools.register(defineTool({...}))`），按用途分十组：

### 3.1 靶标与资产（10）

```
redteam_engagement_open        绑定本次演练靶标，创建工作区（写 current 指针）

redteam_asset_query            检索（cidr/port/service/fingerprint/scope/q/sort/state）
redteam_asset_get              单资产完整详情（端口、指纹、采集时间线、关系边）
redteam_asset_stats            测绘概览（C 段数、资产、存活、端口、服务、指纹、各 C 段明细）
redteam_asset_graph            资产图谱导出（C 段 → 资产 → 端口 + 解析边）
redteam_asset_link             写关系边（resolves / exposes / contains / trusts / shares_cert）
redteam_asset_assess           易打性评估（priority high|medium|low + potential + reason）
redteam_asset_test             测试状态流转（untested/testing/tested/blocked/abandoned/no_surface）
redteam_domain_index           域名维度聚合（域名 → 子域 → IP → C 段）
redteam_web_list               Web 资产清单（URL + 标题）
```

### 3.2 漏洞与证据（4）

```

                                    gained 字段记「通过它拿到了什么权限」
redteam_http_evidence_add           原始 HTTP 请求/响应（报告渲染成可粘贴进 Yakit 的报文）
```

### 3.3 凭据与会话（4）

### 3.4 入口：WebShell 与隧道（7）

```

redteam_sessions                        【每次派任务前先看】WebShell / 隧道 / 凭据 / 会话一屏总览
```

### 3.5 攻击链与图谱（4）

```
redteam_chain_add    攻击链步骤（stage + stage_code + 可选 point_code/evidence 联动记分）
redteam_chain        完整链路（按 seq）
redteam_attack_chain 【指挥中枢】五阶段 + 每阶段拿到多少分与累计分 + 涉及资产 + 真实隧道
redteam_attack_path  攻击图谱（资产拓扑 + 漏洞节点 + 已控制资产）
```

### 3.6 攻击文件与报告（4）

```
redteam_score_report             攻击得分链路复现报告（**唯一交付报告**，只收录得分成果）
redteam_report / report_targets  【已弃用】旧成果报告，保留兼容
```

### 3.7 得分目标（3）

```
redteam_score_list / score_hit / score_point_save   读分 / 记分 / 维护得分点
```

```

redteam_poc_get           取全文（含落盘路径）
redteam_poc_add / update  回填与补验证（verified + verified_note）
redteam_poc_list / use    盘点 / 记一次复用（hit_count 累加）
```

```
redteam_role_prompt / redteam_roles / redteam_role_prompt_reset
```

### 3.10 工具契约的三条硬规则

1. **每次发现必带来源**：`provenance`（passive/active）+ `tool`，界面据此标色，保证"这条数据是谁扫出来的"可信。
2. **写操作必须给证据**：如攻击文件的 `evidence`、得分的 `evidence`，避免"无证据的成果"。
3. **schema 必须合法**：DSH 在挂载预设时校验每个工具的 schema，一旦不合法（典型：`type: 'object'` 漏写 `additionalProperties`）**整个预设 mount 失败** → 会话无法 resume → 客户端命令菜单无限重试 → dsh 进程 CPU 打满、界面卡死。**改完 schema 必须跑 `tool-schema.test.mjs`**（v0.6.1 真出过这个事故）。

## 5. 技术框架（一）：包与平面

DSH 的组合（composition）分 **host 平面**与 **agent 平面**，各包严格按平面归位。理解这张表，就理解了本项目的架构：

| 包 | 平面 | 职责 | 关键实现 |
| --- | --- | --- | --- |
| `dsh-redteam-store`<br/>`packages/redteam-store` | **host** | 数据核心：靶标工作区（目录 + `engagement.yaml`）、SQLite 事实库（schema/写入/查询）、提示词与技能文件读写、**连通性探测**（智能体的沙箱连不出去，只有 host 能真实发起连接）。发布进程级服务 `ctx.redteam`；另有 JSON-in/out CLI | `lib/core.js`（3450 行，零 Cordis 依赖）+ `lib/index.js`（Cordis 壳）+ `bin/cli.mjs` |
| `dsh-redteam-tools`<br/>`packages/redteam-tools` | **agent** | 48 个 `redteam_*` 模型工具，把事实库、得分目标、会话入口暴露给智能体。只向 `tools` 注册工具、不发布服务，故不需要 isolate realm | `lib/index.js`（1146 行） |
| `dsh-redteam-ui`<br/>`packages/redteam-ui` | **host + client** | 控制台。host 半侧注册 `POST /redteam/api` 桥接 `ctx.redteam`（含异步 `probeSessions`）与技能目录；浏览器半侧是常驻右侧栏 UI | `lib/index.js`（171 行）+ `lib/client.js`（2993 行手写 bundle） |
| `dsh-redteam-mode`<br/>`packages/redteam-bundle` | **市场包** | 自包含单包：`lib/` 由 `tools/build.mjs` 从上面三个包**生成**，预设与 13 个技能一并打包，供 `dsh plugin add` 一条命令安装 | `cordis.patch.yml` + `presets/redteam/` + `skills/` + `tools/build.mjs` |

```
DSH host 平面                          DSH agent 平面（redteam 预设）
─────────────────────────              ─────────────────────────────────
cordis.patch.yml 插入三行:              preset/agent.cordis.yml:
  redteam-mode      (自举预设+技能)        persona        (指挥者人设, prefix)
  redteam-mode/store → ctx.redteam        redteam-tools  → 48 个模型工具
  redteam-mode/ui   → /redteam/api        skill-filesystem + tool-skill
                                          tool-bash/fs/jobs/web/ask-user/todo
                                          delegation     (subagent, maxDepth 1)
                    ▲                          │
                    │  ctx.redteam (进程级服务) │
                    └──────────────────────────┘
        浏览器 ── POST /redteam/api ──▶ ui host 半侧 ──▶ store (同一份 core.js)
        命令行 ── node bin/cli.mjs ──▶ 同一份 core.js
```

**"同一份 core.js"是刻意的**：界面看到的、智能体查到的、命令行验的，都是同一实现，行为不会漂移。

### 5.1 关键接口

**客户端 ↔ host**：单一具名路由 `POST /redteam/api`（`kind: 'exact'`），为什么不用 typert/@Remote？因为这两个包刻意保持**零外部依赖**（profile 下解析不到 node_modules），具名路由是最小且稳定的接缝。跨源请求由 Origin/Host 比对挡住（同源才放行），请求体上限 8 MiB，响应统一 `application/json; charset=utf-8` + `no-store`。

请求体是 `{ op: '...', ... }`，`dispatch()` 处理同步 op（bootstrap / openEngagement / activateEngagement / pocSearch / 资产查询 / 得分 / 报告 …），`dispatchAsync()` 只多处理一条 `probeSessions`（真实发起 HTTP/TCP 连接）。

**技能目录**：`skillCatalog` / `skillRead` 两个 op 按红队 preset 的 standing scope（`ctx.agentPresets.standingKeyFor('redteam')`）读 `ctx.skills` 原生注册表，并如实标出每个技能来自哪个目录/哪个 provider（避免用户看到几百个技能以为是本插件塞的）。

**连通性探测（host 专有）**：`probeSessions()` 对每个 WebShell 发一次不带参数的 `GET`（`status < 500` 记 online），对每条隧道做一次 TCP `connect`（默认超时 6000ms，可调 1000–20000ms），回写 `status / last_check / latency_ms / check_note`。

### 5.2 预设：`preset/agent.cordis.yml`（396 行）

这是 **agent 平面**的组装文件，由 `standard` 预设改造而来。要点：

- **identity**：`dsh-persona` 的 `prefix` 就是那段"红队作战指挥智能体"人设（授权前提 / 只打得分面 / 得分目标 / 优先打什么 / Nday 工作流 / 首要规则 / 查库 / 已有入口 / 工具技能优先 / 代理使用 / 攻击文件纪律 / 记分纪律 / 报告口径 / 攻击链五阶段）。注意新版 `dsh-persona` 用 `prefix`/`suffix`，旧的 `text` 字段会导致挂载失败。
- **realm 规则**：文件里每个发布服务的 `cordis:group` 都必须带 `isolate`（`planMode` / `compaction` / `toolResultPruner` / `workflowEngine` 各有自己的 realm），否则会发布进 root realm、与其他预设撞名。
- **红队工具行**：`- id: redteam-tools / name: dsh-redteam-tools`（bundle 里改成 `dsh-redteam-mode/tools`）。
- **委派**：`tool-subagent`（provider=spawn, `backgroundMode: continuable`, `maxDepth: 1`, toolFilter.deny 三个工具）+ `tool-subagent-fork` + `tool-workflow` + `tool-ralph`；`subagent_codex` / `subagent_claude_code` 两行 `disabled: true`（生产 dsh 不装这两个 provider）。
- **其余模型可见行**：bash/pwsh（按平台 disabled）、fs/fs-search、jobs、skill、goal、plan-mode、compaction、todo、ask-user、web。

### 5.3 市场包与构建

**为什么"生成"而不是"直接依赖"**：pnpm 默认隔离布局，`dsh-redteam-store` 这类**传递依赖**不会被链到 `<profile>/node_modules/` 下，而预设里的行按宿主 base 解析裸包名（`loader.internal.import(name, profileDir)`）——一旦引用传递依赖就直接解析失败。所以让市场用户**只装一个包、包内自带全部实现**是唯一稳的做法。

`tools/build.mjs`（154 行）做的事：

1. 拷 `redteam-store/lib/core.js` → `lib/store-core.js`；插件壳里的 `./core.js` 改成 `./store-core.js`；
2. 拷 UI host 半侧 → `lib/ui.js`（把 `../../redteam-store/lib/core.js` 改成本地 `./store-core.js`）；
3. 拷客户端 → `lib/client.js`，并把 `__ModuleLoader__.load({ id })` 的 id 改成**本包包名** `dsh-redteam-mode`（前端加载器按包名认领模块，不改会报 "loaded without registering"）；
4. 拷工具集 → `lib/tools.js`（改本地 `store-core.js` 引用）；
5. 生成预设 `presets/redteam/agent.cordis.yml`：工具行指向本包子路径；`skill-filesystem` 行注入 `includeDefaultRoots: false` + `customSkillDirs: [{{REDTEAM_SKILLS_DIR}}, $DSH_HOME/skills]`——**只扫"本插件自带 + $DSH_HOME/skills"两个根**，避免把 `.agents/skills`、项目级大技能包（动辄数百个）一起吞进红队会话，污染模型上下文；
6. 拷 13 个技能、拷 `preset.yml`；
7. **校验**：生成的 lib 里不允许残留跨包相对路径或 `redteam-(store|ui|tools)` 引用，预设必须生成。

`--check` 模式只比对不写盘，**任何漂移都以非零码退出**，用于 CI 与 `prepublishOnly`。

### 6.2 迁移与自愈

`migrate(db)` 走**先查 `PRAGMA table_info` 再 `ALTER TABLE ADD COLUMN`** 的轻量路线，重复执行安全，老靶标库不需要重建。它同时承担多项**自愈**：

- 清掉废弃阶段值（`external/foothold/tunnel/privilege`）与旧版 `target` 行，保证阶段表只剩 5 个合法 code；
- 老攻击步骤按 `LEGACY_STAGE_MAP` 回填 `stage_code`（`vuln/exploit → internet`、`access/data → internal`、`pivot → boundary`、`other/recon → recon`）；
- 老库按 IP 回填 `asset.scope`；
- 逐列补新字段（`vuln.gained`、`credential.secret_value`、`score_hit.self_created/vuln_id/step_id`、`attack_step.point_id`、`tunnel.entry_kind` …）。

> 已有的坑：`'target'` 在新老两版阶段表里**同名**，删除语句必须按 `(code, name)` 精确匹配，否则第二次打开靶标会把新版「⑤靶标权限」删掉 → 报告少算 40 分（v0.4.2 修，并有回归测试锁住）。

### 6.3 提示词版本管理（值得单独学）

- 每个靶标把四个角色的提示词存在 `engagements/<靶标>/agents/{recon,vuln-scan,exploit,internal}.md`，指纹记录在同目录 `.defaults.json`。
- 语义：**是内置默认 → 跟着新版走；用户自己改过 → 永不被覆盖**。判定靠 sha1 前 12 位指纹比对，历史默认版本登记在 `LEGACY_PROMPT_HASHES`。
- 为什么需要 `LEGACY_PROMPT_HASHES`：v0.7.6 的四个默认指纹曾经只存在于各靶标的 manifest 里，manifest 一旦丢失（靶标被拷到别的机器 / 目录被清过），那批默认版本就会被**误判成"用户自己写的"而永不升级**——批量升级时差点误判为"覆盖了用户自写"。
- 批量升级：`node scripts/refresh-all-prompts.mjs [--dry-run]`（复用服务端的 `refreshDefaultPrompts`，语义与面板完全一致，自动 `.bak-<时间戳>` 备份，输出里出现 `用户自写(保留)` 即表示该角色被人工改过、脚本不会覆盖）。

### 6.4 数据落点与工作区


### 6.5 三个入口，一份实现

| 入口 | 路径 | 用途 |
| --- | --- | --- |
| DSH 模型工具 | `ctx.redteam`（`redteam_*`） | 智能体的日常读写 |
| HTTP 桥接 | `POST /redteam/api`（`{op, ...}`） | 浏览器控制台 |
| CLI | `node packages/redteam-store/bin/cli.mjs`（stdin JSON → stdout JSON） | 不启界面就查库/灌数据/排障；`redteam-proto/store.mjs` 只是它的转发壳 |

三者都走 `core.js` 的同一份 `dispatch`，因此行为一致。

### 6.6 纪律：数据与密钥

- 所有演练数据只写**本机**；项目不含遥测/上报/云端同步代码。
- **凭据明文入库**（`credential.secret_value` / `webshell.pass_key`），面板直接显示便于复用，同时 `secret_ref` 指向 `runs/` 证据。**这个库文件是最高敏感度资产**：不要复制、导出、提交到任何仓库/聊天工具。
- `.gitignore` 已排除 `engagements/`、`runs/`、`pocs/`、`toolkit/`、`*.db`、`*.jsonl`、`*.pcap`、`.env`、`secret*`、`token*`、`credential*` 等。
- 仓库里**不含任何真实密钥或基础设施地址**：VPS 一律是 `<你的VPS_IP>` 占位符；FOFA 等 key 从环境变量读（`FOFA_KEY`）。

## 7. 知识库与 Nday 工作流

打已知漏洞的标准顺序（**先查库 → 再互联网 → 最后手搓**）：

```
① redteam_poc_search(组件/版本/CVE/正文特征串)
     ├─ 知识库命中 → redteam_poc_get 取全文直接用，redteam_poc_use 记一次复用
     └─ nuclei 模板命中 → nuclei -t <相对路径> -u <目标>
② 两层都没有 → web_search / GitHub / ExploitDB / 厂商公告 / CNVD·CNNVD
③ 还没有（或残缺/收费）→ 自己手搓，最小验证原则（先证明存在，再谈深度）
④ 验证有效 → redteam_poc_add 回填：title/kind/cve/component/versions/language/
              source(web|self|manual|nuclei-template)/source_url/usage/content/
              verified + verified_note；后来验证的用 redteam_poc_update 补
⑤ 回填必须脱敏：去掉内网真实地址、自己的 VPS/域名、本次靶标专属参数，只留通用部分
```

知识库条目的 `code` 是稳定 slug（`slugPoc`：CVE + 标题，标题已含 CVE 时不重复拼），正文按语言落盘为 `pocs/<code>/poc.{py,sh,yaml,…}`，方便智能体直接运行。检索排序是"**已验证 → 复用次数高**"优先 —— 后来者优先选经过实战的武器。

**nuclei 模板搜索**：`nucleiTemplatesDir()` 依次找 `$DSH_HOME/redteam/toolkit/nuclei-templates`、`~/.local/nuclei-templates`、`~/nuclei-templates`、`/usr/share/nuclei-templates`、`/opt/nuclei-templates`（本机命中第二个，13619 个 yaml）。

**知识库 ≠ 攻击文件**：换任何目标都能用的通用 POC/EXP 进知识库（跨靶标共享）；只对本次靶标有效的脚本/配置进攻击文件（`attack-files/<目标>/`，且必须有"实际打通的证据"）。**通用武器别埋在某个靶标的目录里。**

## 8. 技能（13 个原生技能）

技能以 DSH 原生技能体系管理（`$DSH_HOME/skills`、项目 `.dsh/skills`、`.agents/skills`），随包分发的 13 个在 `skills/`。每个技能是带 frontmatter 的 Markdown（`name` / `description` / `whenToUse` / `role` / `enabled`），智能体用原生 `skill` 工具按需加载。

| 技能 | 角色 | 用途 |
| --- | --- | --- |
| `passive-recon` | recon | 被动信息收集：不接触目标主机，仅用公开数据源（crt.sh 等） |
| `active-scan` | recon | 主动端口与服务扫描（nmap/masscan），严格遵守授权范围 |
| `web-fingerprint` | recon | Web 指纹：框架/中间件/CMS/组件版本（注意 PD 版 httpx 要用 `pd-httpx`） |
| `asset-correlation` | recon | 资产关联：域名↔IP↔C 段↔证书↔服务的图谱化（走 `redteam_asset_link`） |
| `fofa-recon` | recon | FOFA API 批量测绘（限速客户端，避免 45012；key 读 `FOFA_KEY`） |
| `browser-automation` | recon | 无依赖驱动 headless Chrome：抓 JS 渲染页、截图、执行 JS、抓接口清单 |
| `kimi-webbridge` | recon | Kimi 浏览器扩展驱动用户真实 Chrome：复用登录态、真实浏览器指纹 |
| `cn-proxy-pool` | vuln-scan | 国内免费 HTTP/SOCKS5 代理池（**只用命令级代理参数**，不改本机配置） |
| `vps-reverse-shell` | exploit | 自建 VPS 做反弹 shell 落地与中转（9000–9999 监听、非交互会话驱动、载荷投递） |
| `webshell-toolkit` | exploit | 冰蝎/哥斯拉/蚁剑：**无 GUI 生成冰蝎马**（密钥 = `md5(密码)[:16]`）并落库 |
| `suo5-tunnel` | internal | **打进内网的标准通道**：经 WebShell/HTTP 建 socks5，登记 + 实测连通 |
| `gogo-intranet` | internal | gogo v2.15.0 内网测绘引擎（智能/超智能、主被动指纹、关键信息提取、nuclei 模板 POC） |
| `fscan-intranet` | internal | fscan v2.2.1 内网普查（存活/端口/28 类弱口令/未授权/高危漏洞/Redis 利用） |

外部工具建议放在 `$DSH_HOME/redteam/toolkit/`：nmap、masscan、nuclei、sqlmap、ffuf、httpx(PD)、naabu、subfinder、dnsx、dirsearch、gogo、fscan、suo5、chisel、frp，以及冰蝎/哥斯拉/蚁剑。

## 9. 开发指南

### 9.1 从源码装（开发者）

三个源码包是**唯一源码**，`packages/redteam-bundle` 是生成物。让 profile 能按包名解析到它们：

```bash
PROFILE=~/.dsh/profiles/web
mkdir -p "$PROFILE/node_modules"
for p in redteam-store redteam-tools redteam-ui; do
  ln -sfn "$PWD/packages/$p" "$PROFILE/node_modules/dsh-$p"
done
# dsh-redteam-tools 需要宿主提供 @deepseek-ai/dsh-tools，按你的 DSH 安装方式补软链
# profile/cordis.patch.yml 追加 redteam-store / redteam-ui 两行；再拷预设与技能：
mkdir -p ~/.dsh/.agent-presets/redteam ~/.dsh/skills
cp preset/agent.cordis.yml preset/preset.yml ~/.dsh/.agent-presets/redteam/
cp skills/*.md ~/.dsh/skills/
```

**从预发布版升级**（0.7.0 之前装过开发版，profile 里有手写行）：

```bash
cd ~/.dsh/profiles/web

```

### 9.6 常见坑（都是真实踩过的）

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| 工具 schema 缺 `additionalProperties` | 整个预设 mount 失败 → 会话无法 resume → 命令菜单无限重试 → CPU 打满 | 跑 `tool-schema.test.mjs` |
| `deny` 里写了 `subagent` | 委派路径报 "unknown global tool"（scoped 工具不在全局库） | 只 deny `subagent_fork`/`workflow`/`ralph`，靠 `maxDepth: 1` 兜底 |
| 预设行 id 撞车 | boot 直接失败：`duplicate loader entry id` | 市场包所有行 id 带 `redteam-mode-` 前缀 + `(id+name)` 精确匹配关旧行 |
| 客户端 bundle 注册 id 写错 | 面板加载失败："loaded without registering" | build 时把 `__ModuleLoader__.load({id})` 改成**包名** |
| 阶段 code 自造值 | 步骤不落在任何阶段，页面计数为 0 | 只用 5 个合法值；服务端已加白名单与 `stage_hint` |
| 隧道漏填 `entry_kind` | `legit=null`、"待确认"、不计边界突破 | 登记时必填；历史隧道用 `redteam_tunnel_update` 补 |
| `redteam_asset_test` 的 `notes` | 早期 schema 里不存在 → 静默丢弃，"排除结论/登录失败原因"全没落库 | 已修：`notes` 作为 `test` 的兼容别名，一并追加进 `test_notes` |
| `chain_add` 带 `point_code` 不带 `evidence` | 静默跳过记分，模型以为记上了 | 已修：回 `score_hint` 明确告知"本次没有记分" |
| 提示词改了不生效 | 角色提示词**按靶标**存，只在读取时比对升级 | 用 `scripts/refresh-all-prompts.mjs` 批量刷新 |
| `dsh-persona` 用旧 `text` 字段 | 挂载失败（新版要 `prefix`/`suffix`） | 保持 `prefix:` 写法 |

## 10. 学习路径与动手实验

### 10.1 建议节奏（3 天）

**第 1 天：跑通闭环**

1. 读 `README.md` §1–3，重启 `dsh web`，确认右侧栏出现 RedTeam 面板；
2. 新建会话选预设**红队模式**，打开「得分目标」页看 10 个得分点；
3. **用 `示例科技有限公司` 这个假靶标练手**（`203.0.113.0/24` 是 RFC 5737 文档网段，不会碰真实目标）：
   - `node packages/redteam-store/bin/cli.mjs` 灌一组 stdin JSON 看数据怎么进库；
   - 或 `node redteam-proto/seed-demo.mjs | node redteam-proto/store.mjs`；
   - `node redteam-proto/seed-findings.mjs` 灌漏洞/凭据/会话，看攻击图谱与报告；
4. 在页面里点：资产测绘 → 攻击链 → 得分目标 → 报告，理解"一条得分怎么出现在报告里"。

**第 2 天：读代码**

1. `packages/redteam-store/lib/core.js`：先读 DDL（约 50–270 行）、`DEFAULT_STAGES`、`scoreStageOf`、`DEFAULT_SCORE_POINTS`、`DEFAULT_PROMPTS`、`dispatch`、`probeSessions` 这几段；
2. `packages/redteam-tools/lib/index.js`：随便挑 3 个工具（建议 `asset_add`、`score_hit`、`tunnel_add`），看参数 schema 与返回值约定；
3. `packages/redteam-ui/lib/index.js`（171 行，最好读）+ `client.js` 的任一个页签实现；
4. `preset/agent.cordis.yml`：对着 §5.2 逐段看，特别留意 realm 规则与委派硬约束。

**第 3 天：真靶标演练（须有授权）**

按 §10.2 的清单走一遍，重点体会"**得分点驱动**"与"**打之前先查库**"两条纪律。

### 10.2 一次演练的标准动作清单

```
① redteam_engagement_open(靶标名[, scope])     建/开工作区，写 current 指针
② redteam_score_list                            读分：满分多少、已经拿了什么
③ redteam_role_prompt('recon')                  取角色提示词，塞进子智能体任务
④ subagent(信息收集…)                           收集资产 → asset_add/assess/test
⑤ 按易打性排序 → subagent(漏洞检测…)             Nday 优先；poc_search → get/模板 → 验证
⑥ 拿到入口 → webshell_add / tunnel_add(带 entry_kind) + chain_add(stage_code)
⑦ redteam_session_check                         实测连通性，掉线的标 down
⑧ 每个成果 → score_hit(code + evidence [+vuln_id])
⑨ redteam_attack_chain                          对表：现在第几阶段、各阶段拿了多少分
⑩ redteam_score_report                          出报告（只含得分成果 + 原始请求）
```

### 10.3 自检题（能答上来就算学会）

1. 一条得分落在哪个阶段，是**谁**决定的？四种优先级分别是什么？
2. 为什么 `entry_kind` 留空会丢分？`self-only` 与 `target-http` 的区别是什么？
3. 拿到了一个账号口令，为什么**不能**直接记 `web-account-admin`？
4. 为什么市场包要从三个源码包"生成"而不是直接依赖？
5. `attacks_step.stage_code` 写 `foothold` 会怎样？服务端怎么兜底？
6. 为什么角色提示词要按**靶标**存储？如何批量升级？
7. 知识库和攻击文件的边界在哪？回填 POC 前必须做什么？
8. 改了一个工具的 schema，发版前**必须**跑哪个测试？不跑的后果是什么？
